Capitulo 5

Evaluacion profunda, thresholds y analisis de error

Una gran cantidad de proyectos fracasa no porque el modelo sea técnicamente malo, sino porque fue evaluado de forma ingenua. La evaluación en machine learning no consiste en imprimir una métrica bonita. Consiste en construir una aproximación honesta al comportamiento del sistema bajo las condiciones en las que realmente será usado.

5.1 Train, validation y test no son nombres decorativos

La separación entre entrenamiento, validación y test cumple una función metodológica. Train sirve para ajustar parámetros. Validation sirve para comparar enfoques, seleccionar umbrales e hiperparámetros. Test sirve para obtener una estimación final. Si consultas el test una y otra vez, deja de ser un test; se convierte en otra validación contaminada.

La lógica aquí es sencilla: cada vez que miras el test y cambias una decisión en función de ese resultado, estás aprendiendo algo del test y adaptándote a él. Eso erosiona la honestidad de la evaluación.

5.2 Accuracy: por qué a menudo es una trampa

Accuracy es intuitiva, y precisamente por eso seduce demasiado. Pero en problemas desbalanceados suele ser una métrica floja. Si el fraude ocurre en 1 por ciento de las transacciones, un modelo que diga “no fraude” siempre tendría 99 por ciento de accuracy y sería completamente inútil.

La pregunta correcta no es “qué accuracy tengo”, sino “qué comportamiento operativo induce este sistema”.

5.3 Precision, recall y la forma correcta de pensarlos

Precision responde: de lo que marqué como positivo, cuánto realmente lo era. Recall responde: de todos los positivos reales, cuántos capturé. Pero no basta recitar esto. Debes conectarlo con costos reales.

  • En fraude, recall alto puede ser crucial si dejar escapar fraude es muy caro.
  • En una revisión humana limitada, precision también importa mucho porque demasiados falsos positivos saturan al equipo.

Por eso las métricas no se eligen solo por elegancia matemática; se eligen por estructura de costos y capacidad operativa.

5.4 PR-AUC y ROC-AUC

ROC-AUC es útil para medir la capacidad de ranking a través de múltiples thresholds, pero en eventos raros puede seguir viéndose bien aunque el sistema operativo sea pobre. PR-AUC suele ser más informativa cuando el positivo es escaso, porque enfatiza la relación entre precisión y recall en el espacio que más importa.

5.5 Thresholds: la capa donde el score se convierte en acción

Un modelo probabilístico produce scores. El sistema real actúa a través de un threshold o una política. Esa política no es un detalle menor. Es parte central del diseño. Si tu equipo puede revisar solo 200 casos por día, el threshold debe alinearse con esa restricción. Si el costo del falso negativo es enorme, quizá quieras bajar el threshold. No existe un 0.5 universalmente correcto.

import numpy as np
import pandas as pd
from sklearn.metrics import precision_score, recall_score, f1_score

rows = []
for t in np.arange(0.05, 0.96, 0.05):
    pred = (valid_proba >= t).astype(int)
    rows.append({
        "threshold": round(t, 2),
        "precision": precision_score(y_valid, pred),
        "recall": recall_score(y_valid, pred),
        "f1": f1_score(y_valid, pred),
        "positivos_predichos": int(pred.sum())
    })

threshold_table = pd.DataFrame(rows)
print(threshold_table)

Esta tabla es un instrumento de decisión. Te dice cómo cambia el sistema cuando mueves el threshold. Esa es una conversación entre data science y operación, no solo entre modeladores.

5.6 Analisis de error: donde realmente aprendes

Si solo comparas métricas, aprendes poco. Si revisas errores, aprendes mucho más. El análisis de error responde preguntas como:

  • Qué tipos de casos se convierten en falsos positivos.
  • Qué tipo de positivos reales se están escapando.
  • Si hay segmentos sistemáticamente mal tratados.
  • Si falta una señal en las features.
  • Si el problema es ranking, calibración o threshold.
valid_result = X_valid.copy()
valid_result["y_true"] = y_valid.values
valid_result["score"] = valid_proba
valid_result["pred"] = (valid_result["score"] >= 0.35).astype(int)

fp = valid_result[(valid_result["pred"] == 1) & (valid_result["y_true"] == 0)]
fn = valid_result[(valid_result["pred"] == 0) & (valid_result["y_true"] == 1)]

Paso 2. Tabla por thresholds

Usa el bloque anterior de thresholds.

Paso 3. Lift en el top 10 por ciento

valid_eval = pd.DataFrame({
    "score": valid_proba,
    "y_true": y_valid.values
}).sort_values("score", ascending=False)

n_top = int(len(valid_eval) * 0.10)
top = valid_eval.head(n_top)

rate_top = top["y_true"].mean()
rate_global = valid_eval["y_true"].mean()
lift = rate_top / rate_global
print("lift_top_10pct:", lift)

Ahora sí tienes una métrica muy cercana a una política real de campaña.

Paso 4. Revisar errores por segmento

valid_result["canal"] = X_valid["canal"].values

segment_report = valid_result.groupby("canal").agg(
    score_prom=("score", "mean"),
    positivos_reales=("y_true", "mean"),

Si el sistema trata de forma muy distinta a segmentos relevantes, eso debe entrar en la recomendación final.

Idea central: la evaluación correcta no es “qué score obtuvo el modelo”, sino “qué sistema estoy construyendo cuando convierto este score en decisiones”.

Capitulo 6

Forecasting serio: cómo construir pronósticos útiles y no modelos optimistas

El forecasting exige una forma de pensar distinta. Aquí no basta con “tener una columna fecha”. En series de tiempo, la estructura causal del tiempo es el problema mismo. Si violas esa estructura, tu evaluación deja de parecerse al mundo real y tus resultados se vuelven artificialmente optimistas.

6.1 Lo que hace distinto a un problema temporal

En clasificación o regresión tabular, un split aleatorio puede ser razonable en muchos casos. En forecasting suele ser incorrecto. La razón es simple: en producción, siempre predecirás el futuro desde el pasado. Mezclar ambos en validación rompe la causalidad del problema.

6.2 Componentes de una serie

Una serie temporal puede combinar:

  • Tendencia.
  • Estacionalidad.
  • Ciclos.
  • Eventos o shocks.
  • Ruido.

Un error común es tratar todo como si fuera una función suave y estable. En negocio, promociones, quiebres de stock, feriados y cambios operativos pueden alterar drásticamente la dinámica.

6.3 Baselines temporales

Antes de cualquier modelo sofisticado, necesitas baselines simples pero fuertes:

  • Último valor observado.
  • Mismo día de la semana anterior.
  • Promedio móvil.
  • Promedio histórico por día de semana.

Si tu modelo no supera claramente estos baselines, probablemente no merece despliegue.

6.4 Features temporales correctas

df = df.sort_values("fecha")
df["lag_1"] = df["ventas"].shift(1)
df["lag_7"] = df["ventas"].shift(7)
df["lag_28"] = df["ventas"].shift(28)
df["ma_7"] = df["ventas"].shift(1).rolling(7).mean()
df["ma_28"] = df["ventas"].shift(1).rolling(28).mean()
df["dow"] = df["fecha"].dt.dayofweek
df["month"] = df["fecha"].dt.month

El detalle técnico importante es el shift(1) antes de la media móvil. Sin eso, estarías usando el valor del mismo día dentro de la feature, lo que equivale a meter información del objetivo en la entrada.

6.5 Backtesting

Backtesting significa simular varios puntos históricos de entrenamiento y validación. No te interesa solo un corte arbitrario. Te interesa ver cómo habría funcionado el modelo repetidamente si hubieras vivido en distintos momentos del pasado.

Ese patrón es crucial porque una sola ventana puede favorecer o perjudicar artificialmente a un enfoque.

Paso 5. Modelo supervisado

from sklearn.ensemble import RandomForestRegressor

feature_cols = ["lag_1", "lag_7", "lag_28", "ma_7", "ma_28", "dow", "month"]

rf = RandomForestRegressor(
    n_estimators=400,
    min_samples_leaf=3,
    random_state=42
)

rf.fit(train[feature_cols], train["ventas"])
pred = rf.predict(valid[feature_cols])

mae_model = mean_absolute_error(valid["ventas"], pred)
print("MAE model:", mae_model)

Paso 6. Errores por segmento temporal

valid_eval = valid[["fecha", "ventas"]].copy()
valid_eval["pred"] = pred
valid_eval["abs_error"] = (valid_eval["ventas"] - valid_eval["pred"]).abs()

print(valid_eval.groupby("month")["abs_error"].mean())

Capitulo 7

Causalidad y experimentacion: porque predecir bien no basta

Un modelo predictivo puede decirte quién probablemente hará algo. Pero muchas decisiones de negocio no preguntan eso. Preguntan otra cosa: qué pasará si intervengo. Esa es una pregunta causal, no predictiva. Confundir ambas es una de las fuentes más persistentes de decisiones equivocadas en data science aplicada.

7.1 Predicción vs efecto de intervención

Supongamos que construyes un modelo que identifica clientes con alta probabilidad de comprar. Eso no significa automáticamente que ofrecerles un descuento aumentará compras. Quizá comprarían de todas formas. La pregunta predictiva es “quién comprará”. La pregunta causal es “a quién conviene ofrecer descuento para cambiar el resultado”. Son preguntas diferentes.

7.2 Qué resuelve un A/B test

Un experimento aleatorizado busca estimar el efecto de una intervención reduciendo sesgos sistemáticos entre grupos. Su fuerza está en que, idealmente, la randomización rompe la correlación entre tratamiento y otros factores no observados.

Un diseño mínimo incluye:

  • Hipótesis.
  • Población elegible.
  • Tratamiento y control.
  • Métrica primaria.
  • Duración o criterio de tamaño muestral.
  • Regla de decisión predefinida.

7.3 El problema de los observacionales

Si en datos históricos el equipo comercial contactó antes a los clientes más prometedores, entonces “haber sido contactado” probablemente estará asociado a una mayor conversión. Pero esa asociación no implica que la llamada haya causado toda la diferencia. Ahí entra el sesgo de selección.

7.4 Tutorial: diseñar un experimento de email

Pregunta

Queremos saber si una nueva versión de email aumenta la conversión a 7 días.

Diseño

  • Población: clientes activos elegibles para campaña.
  • Tratamiento: nuevo email.
  • Control: email actual.
  • Métrica primaria: tasa de conversión a 7 días.
  • Métricas secundarias: apertura, click, unsubscribe.
  • Duración: hasta alcanzar tamaño muestral mínimo o dos semanas, lo que ocurra después.

Error frecuente

Cambiar la métrica principal después de ver los resultados. Eso degrada la credibilidad del experimento.

Capitulo 8

Produccion, monitoreo y MLOps: convertir un modelo en sistema

Un notebook con una métrica alta no es un producto. Un sistema de ML en producción necesita contratos, versionado, monitoreo y criterio operativo. Este capítulo busca que dejes de pensar en el modelo como objeto aislado y empieces a verlo como parte de una arquitectura mayor.

8.1 Batch vs realtime

Elegir realtime por prestigio técnico es un error común. Muchas decisiones no requieren latencia de milisegundos. Un scoring batch diario puede ser más que suficiente para campañas, pricing programado, riesgo periódico o forecast operativo. Batch suele ser más simple, más barato y más robusto.

8.2 Qué debe versionarse

  • Código.
  • Snapshot o referencia de datos de entrenamiento.
  • Pipeline de features.
  • Artefacto del modelo.
  • Métricas observadas.
  • Configuración del experimento.

Versionar solo el archivo del modelo es muy poco. Si no puedes reconstruir cómo se entrenó, no tienes trazabilidad real.

8.3 Monitoreo: más allá de latencia y errores HTTP

El monitoreo técnico importa, pero no basta. Un sistema de ML también debe monitorear:

  • Distribución de features de entrada.
  • Distribución de scores.
  • Tasa de cobertura.
  • Drift respecto al entrenamiento.
  • Calidad de datos de entrada.
  • Performance posterior cuando existan labels tardías.

8.4 Tutorial mínimo de servicio de predicción

from fastapi import FastAPI
import joblib
import pandas as pd

app = FastAPI()
model = joblib.load("model.joblib")

@app.post("/predict")
def predict(payload: dict):
    df = pd.DataFrame([payload])
    score = float(model.predict_proba(df)[:, 1][0])
    return {"score": score}

Este ejemplo es deliberadamente mínimo. Le faltan validación, autenticación, versionado, logging estructurado, timeouts, manejo de fallos y monitoreo. Precisamente por eso es útil: te muestra cuántas capas hay entre “tengo un modelo” y “tengo un sistema serio”.

8.5 Criterio de retraining

Un sistema de ML no se entrena una vez y se olvida. Debes definir cuándo volver a entrenar. Las razones pueden ser:

  • Drift fuerte en entradas.
  • Caída de performance observada.
  • Cambio de negocio o definición del target.
  • Ingreso de nuevas fuentes de señal.

También debes decidir si el retraining será periódico, por evento o híbrido.

Idea central: producción no es “poner una API”. Es diseñar un sistema que siga siendo confiable cuando cambian los datos, las operaciones y las condiciones del negocio.
